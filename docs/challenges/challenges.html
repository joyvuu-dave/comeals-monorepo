1 An email change can take over an account Not started security
Opened 2026-11-07 · reviewed 2026-11-07 · docs/challenges/0001-email-change-account-takeover.md
Watches 2 files
  • app/views/resident_mailer/email_change_notice_email.text.erb
  • app/services/email_change.rb

The challenge

Someone who has a resident’s signed-in device for one minute must not be able to take the account away from them for good.

The case that breaks it

  1. A resident is signed in on a phone or laptop that someone else can pick up.

  2. That person opens the profile and changes the email to their own address. No password is asked (ADR 0014, the owner’s choice on 2026-11-05).

  3. They click the link that arrives in their own inbox. The email is now theirs.

  4. They use “forgot password” with the new address and set a new password.

  5. The real resident gets the notice at the old address. It says to sign in and put the old address back. But the password has changed, so they cannot sign in. Only an admin can fix it.

Where we stand

  • The notice to the old address has no link that undoes the change. It says “sign in, open your profile, and put this address back, or ask an admin” (app/views/resident_mailer/email_change_notice_email.text.erb).

  • An email change waits for a one-use link sent to the new address, which works for 24 hours (app/services/email_change.rb, docs/adr/0014-residents-edit-their-own-profile.md).

  • No password is asked for any profile change. This was decided, and this challenge does not reopen it.

Options

  1. A “this wasn’t me” link in the notice. One click undoes the change, puts the old address back, signs out every session, and blocks email changes for that resident for a day. It needs a second token, sent only to the old address. It does not ask for a password.

  2. Wait before a change takes effect. The new address works only 24 hours after the link is clicked, and the old address can cancel during that time. This is slower for an honest change.

  3. Ask for the password on an email change only. Declined by the owner on 2026-11-05 (“don’t ask for their password when they are changing stuff”).

My recommendation is option 1.

2 Keep every guarantee with no database locks we take ourselves Not started concurrency
Opened 2026-11-07 · reviewed 2026-11-13 · docs/challenges/0002-no-explicit-database-locks.md
Watches 3 files
  • app/models/concerns/locks_its_meal_first.rb
  • docs/adr/0003-concurrency-on-the-money-path.md
  • docs/adr/0005-serializable-by-default.md

The challenge

Remove every lock the app takes on purpose, and keep every correctness guarantee the app has.

“No locks at all” cannot happen in PostgreSQL. Every write, unique index and foreign key takes row locks inside the database, whatever the app does. And SERIALIZABLE keeps its own read records inside the database, which Postgres calls predicate locks; they never make anyone wait. So the challenge is: no lock that we take or design ourselves.

The case that breaks it

Take out the locks and change nothing else:

  1. A settlement starts and reads the sign-ups of a dinner.

  2. At the same moment, someone in psql, at READ COMMITTED, adds a sign-up to that dinner.

  3. The settlement commits without the new sign-up. The sign-up commits too. The dinner is settled, and a person who ate is never charged.

The same thing can happen with two people taking the last seat, or a cost written while a dinner is cancelled.

Where we stand

The app protects these rules with four pieces (docs/adr/0003-concurrency-on-the-money-path.md):

  1. with_meal_lock in app/controllers/api/v1/meals_controller.rb takes FOR UPDATE on the meal row for API writes to bills, attendance and guests.

  2. LocksItsMealFirst (app/models/concerns/locks_its_meal_first.rb) makes admin, tasks and the console lock the meal before its rows, so every writer locks in the same order and two writers cannot deadlock.

  3. The settlement takes FOR UPDATE, then claims its meals with a compare-and-swap (app/services/settlement.rb).

  4. The trigger comeals_reject_settled_child_write (in db/structure.sql) writes the meal row on every child write. So a transaction that read that row earlier, even in psql, now conflicts with the write.

The whole app runs at SERIALIZABLE (docs/adr/0005-serializable-by-default.md). The specs that pin the races: spec/db/settlement_race_spec.rb, spec/db/settlement_after_a_raw_write_race_spec.rb, spec/db/cancel_against_a_cost_race_spec.rb.

A TLA+ model of option A, models/SerializableOnly.tla (challenge 28, docs/models.md), finds that a settled dinner keeps its rows when every writer is SERIALIZABLE and a trigger only reads the meal row, and that a psql writer breaks it when there is no check in the database.

Together they make sure:

  • A settlement counts exactly the rows that exist.

  • The rules that read and then write hold: the seat limit, the last open spot, a closed dinner.

  • A collision becomes a wait and a readable 400, not an abort.

Options

A. Let SERIALIZABLE do all of it, and make it required. If every transaction is SERIALIZABLE, Postgres promises the same result as running them one at a time. The gap is a writer that is not SERIALIZABLE, such as psql. Close it with a trigger on every money table that refuses a write unless current_setting('transaction_isolation') = 'serializable'. Then pieces 1 to 4 are no longer needed for correctness. Costs:

  • A wait becomes an abort and a retry, everywhere: admin forms, rake tasks, and a person in psql.

  • A long settlement can be aborted again and again at a busy time, because any sign-up that touches a row it read conflicts with it. It must settle one dinner at a time, or use option B.

  • Under load, Postgres merges its row-level read records into page-level and table-level ones, which can abort transactions that had no real conflict. That means more retries, not wrong data.

  • A database superuser can turn triggers off (session_replication_role = replica). The app’s role on Heroku cannot.

B. An append-only event log, and settlements that name a point in it. Nothing is updated or deleted. Every action is a new row. A settlement says “all events up to point P”, so running it twice gives the same answer, and an event written during it lands after P. The hard part is that commit order is not sequence order: event 104 can commit after event 105 is already read. The standard fix is a cutoff point that only moves forward once no transaction older than it can still be running (pg_current_snapshot(), pg_snapshot_xmin()). Challenge 3 shows a version of B that needs no global sequence. Costs: rewriting bills, attendance and guests as events, and every screen reading computed state.

What either option also needs: an idempotency key on each request, side effects only after commit (done: app/services/live_update.rb), a fixed rule for every tie, and a model checker to show it holds in every ordering (challenge 28).

My recommendation, if this is ever done: A first, and keep with_meal_lock anyway. It is no longer needed for correctness, but it gives people a wait and a clear message instead of a retry.

3 The same guarantees on every database Rails supports Not started portability8 outside facts to read
Opened 2026-11-07 · reviewed 2026-11-11 · docs/challenges/0003-any-database-rails-supports.md
Watches 2 files
  • config/database.yml
  • docs/adr/0008-the-ledger-grain.md

The challenge

The app runs with the same correctness guarantees on any database and version that our Rails version supports: PostgreSQL, MySQL and MariaDB (mysql2 and trilogy adapters), a MySQL Galera cluster, SQLite, and adapters outside Rails such as Oracle and CockroachDB. It does this with no locks we take ourselves (challenge 2), and under heavy use (challenge 4).

The case that breaks it

On a Galera cluster:

  1. A dinner has 11 of 12 seats taken.

  2. Two people sign up at the same moment, on two different nodes.

  3. Each node counts 11 sign-ups, sees a free seat, and adds a row.

  4. The two writes are to different rows, so Galera finds no conflict. Both commit, and 13 people are in a 12-seat dinner.

SERIALIZABLE does not stop this. Galera does not support it across the cluster, and SELECT ... FOR UPDATE locks only on the node where it runs.

Where we stand

The app depends on PostgreSQL in many places:

  • SERIALIZABLE for every session (config/database.yml).

  • Triggers and CHECK constraints in db/structure.sql, which is PostgreSQL SQL.

  • Expression indexes such as the unique index on lower(name).

  • pg_trgm, partial indexes and RETURNING.

  • Money in numeric columns at 8 decimal places (docs/adr/0008-the-ledger-grain.md).

None of this was tried on another database.

Options

The design has to use only what every one of these databases guarantees:

  1. A transaction is all or nothing.

  2. A conditional update of one row is atomic. UPDATE ... WHERE id = 400 AND version = 7 changes 1 row or 0 rows, and two writers cannot both get 1. Rails returns that count from update_all.

  3. A unique index refuses a second copy, including across Galera nodes.

The design: one write list per dinner, with numbered positions.

meal_events(meal_id, position, kind, data, idempotency_key)
UNIQUE (meal_id, position)
UNIQUE (idempotency_key)

A write reads the dinner’s events (say the last position is 37), runs one decision function (“is there a seat? is it closed? is it settled?”), and inserts the new event at position 38. If someone else took 38, the unique index refuses the insert (Galera refuses it at commit), and the write starts again with the new events. Two writes to one dinner always collide on the same key, so every database refuses one of them, at any isolation level. Each dinner has its own positions with no gaps, so the “commit order is not sequence order” problem of a global sequence (challenge 2, option B) does not come up.

Settlement becomes one small step per dinner: append “settled at position 37” at position 38. If a sign-up took 38 first, that dinner’s settlement starts again and includes it. A sign-up that read the dinner before the settlement collides on 38, reads again, and sees “settled”. Settling a dinner twice does nothing the second time. The reconciliation lists each dinner and the position it was settled at, so the cent rounding gives the same answer every time.

What else it needs:

  1. Money as whole units of 10^-8 dollars in a bigint column. SQLite has no real DECIMAL: a decimal value that is not whole is stored as a float, which keeps about 15 to 16 digits, and DECIMAL(16,8) has 16. The ledger already computes in these units (ADR 0008). A bigint holds about $92 billion in them.

  2. Every rule in the one decision function. No triggers (each database writes them differently) and no CHECKs we depend on (see Outside facts). A CHECK can stay as a second check where it works.

  3. Retry a known list of errors, and nothing else: PostgreSQL’s serialization failure, the MySQL and Galera deadlock error (Galera can raise it at COMMIT), SQLite’s busy error, and a unique index refusal on the position key.

  4. An idempotency key per request, so a retry after a timeout cannot sign someone up twice.

  5. Jobs that are safe to run twice (see Outside facts on Galera and SKIP LOCKED).

  6. Side effects only after commit. Done (app/services/live_update.rb).

  7. Text compared in Ruby, not in the database. Store a name_key column that Ruby fills with one rule, and put a plain unique index on it. The same for email. See Outside facts for how the databases compare text.

  8. A person sees their own write. On Galera, a write on node A may not be visible on node B yet. Send each person to one node, or turn on wsrep_sync_wait for those reads.

  9. Order by position, never by time or id. Galera nodes have their own clocks, and Galera’s auto-increment ids have gaps, so a newer row can have a smaller id.

  10. A Rails schema.rb file (not written yet) instead of db/structure.sql. Every PostgreSQL-only feature goes.

What we would lose: today the database refuses a bad write from anyone, including a person in psql. Under this design only writes through the app follow the rules. That becomes finding the problem afterwards: each event stores a hash of the one before it in its dinner’s list, and the daily ledger check verifies the hashes and recomputes everything. A portable design can only use what every database guarantees, and “refuse a bad write from any source” is not on that list.

A TLA+ model of this design, models/MealEventList.tla (challenge 28, docs/models.md), assumes only that a transaction is all or nothing and that a unique index refuses a second row. With the unique index on (meal_id, position), the settled event is always the last one of its dinner and is never written twice; without it, a sign-up can take the same position as the settlement.

How to show it works: run spec/concurrency/ and bin/storm on every database (PostgreSQL, MySQL with both adapters, MariaDB, a 3-node Galera cluster, SQLite). Stop a Galera node while writes run. And write a TLA+ model that assumes only the three guarantees above (challenge 28).

Outside facts

  • Galera does not support SERIALIZABLE across the cluster. SELECT ... FOR UPDATE locks only on its own node, and a conflict between nodes is found at commit and reported as a deadlock error. (checked 2026-11-07: Claude’s memory, not the Galera docs)

  • MySQL before 8.0.16 accepts a CHECK constraint and ignores it. (checked 2026-11-07: Claude’s memory, not the MySQL docs)

  • In MySQL InnoDB, SERIALIZABLE turns plain reads into shared locks. (checked 2026-11-07: Claude’s memory, not the MySQL docs)

  • SQLite stores a non-whole value in a NUMERIC or DECIMAL column as an 8-byte float. (checked 2026-11-07: Claude’s memory, not the SQLite docs)

  • SQLite allows one writer at a time for the whole database. (checked 2026-11-07: Claude’s memory, not the SQLite docs)

  • Oracle’s SERIALIZABLE is snapshot isolation, so two transactions can each read the same rows and write different ones. (checked 2026-11-07: Claude’s memory, not the Oracle docs)

  • MySQL 8’s default text comparison ignores case and accents, so “Jose” equals “José”. Older default comparisons also ignore spaces at the end. (checked 2026-11-07: Claude’s memory, not the MySQL docs)

  • Solid Queue claims jobs with SKIP LOCKED. On Galera that skips only rows locked on the same node. (checked 2026-11-07: Claude’s memory, not the Solid Queue or Galera docs)

4 Many people changing many things at once Not started concurrency1 not checked
Opened 2026-11-07 · reviewed 2026-11-13 · docs/challenges/0004-many-people-many-changes-at-once.md
Watches 1 file
  • docs/concurrency-testing.md

The challenge

The app keeps every guarantee, and stays quick, while many residents change many different things at the same time.

The case that breaks it

At 6 PM, 30 people sign up for dinners, 5 cooks enter costs, someone books the guest room, and a settlement runs. If every write waits on one shared row, or one lock on a whole table, everyone waits in a line, and requests time out.

Where we stand

  • Puma runs 1 thread and 0 workers (AGENTS.md, Heroku section), so the web dyno handles one request at a time. That is for throughput, not safety.

  • Writes to one dinner wait on that dinner’s row (with_meal_lock), so different dinners do not wait on each other.

  • Concurrency is tested at five layers, including an in-process storm in bin/check (spec/concurrency/), bin/storm against a real multi-threaded Puma, and a seeded simulation of the same storm whose failing seeds replay exactly (spec/simulation/; docs/concurrency-testing.md).

  • Not checked: how many requests a second the app handles before people notice a wait.

Options

  1. Measure first. Run bin/storm with as many clients as the community has people, and write down the numbers in this file.

  2. More Puma threads or workers. The locks, not the thread count, make the money path safe (ADR 0003), so this changes throughput only. Each thread needs a database connection.

  3. Keep every write small and touching only its own rows. No row that every write touches, no table locks. The design in challenge 3 has this property: two different dinners never collide.

  4. For many writes to one dinner (everyone at the Common House screen at once): each retry waits a short random time first, so the losers do not all collide again.

5 Time zone rules change Not started time1 not checked1 outside fact to read

The challenge

Dinner times stay right when a government changes its clock rules: the US stops changing clocks, a state moves to another zone, or a country changes its rules with a few weeks’ notice.

The case that breaks it

  1. A law ends daylight saving time in the community’s state.

  2. The server’s time zone data is not updated.

  3. Every dinner after the change shows a start time one hour off, and calendar feeds send it to people’s phones.

The reverse can happen too: a rule changes for past dates, and an old dinner’s start time moves.

Where we stand

  • Every dinner time is turned into an instant in the community’s zone through Community#dinner_start_at. Specs for this include a day the clocks change (spec/models/community_dinner_start_times_spec.rb).

  • Meals store a date, not an instant, so a rule change moves only how a dinner’s time is shown, never which day the dinner is.

  • On Linux, Ruby reads the zone data from the operating system. The tzinfo-data gem is only installed on Windows and JRuby (Gemfile). So on Heroku the data is as new as the Heroku stack.

  • The tests once broke when the Mac’s zone data said one thing and the test expected another (#266).

  • Not checked: how fast Heroku updates its stack’s zone data after a rule change.

Options

  1. Install tzinfo-data on every platform, and update it like any other gem. Then the zone data is in Gemfile.lock, and a rule change is a normal pull request.

  2. A spec that fails when the zone data is older than some number of days.

  3. Leave it to the stack, and watch for announced rule changes for the community’s zone.

Outside facts

  • Linux tzinfo reads /usr/share/zoneinfo unless the tzinfo-data gem is installed. (checked 2026-11-07: Claude’s memory, not the tzinfo docs)

6 Dates far in the future Not started time1 not checked
Opened 2026-11-07 · reviewed 2026-11-07 · docs/challenges/0006-dates-far-in-the-future.md

The challenge

Every part of the app handles any date the database can store, not only dates near the day it was written.

The case that breaks it

Someone types a date in the year 10000, or 2100 (a year that is not a leap year, though it divides by 4), into a dinner, a reservation or an event. One part of the app reads it with a 4-digit year pattern or a JavaScript Date rule that does not hold for it, and the dinner lands on the wrong day or the page fails.

Where we stand

Not checked. PostgreSQL dates go to the year 5874897. Nobody has listed every place the app reads a date (date inputs, URL paths such as /calendar/:type/:date, JSON, calendar feeds) or tested each with a far date.

Options

  1. List every place a date enters the app, and add a spec for each with the dates 2100-02-28, 2100-03-01 and 9999-12-31.

  2. Refuse dates outside a set range (say, more than 10 years from today) at every entry point, and test that the refusal is the same everywhere.

7 Pricing rules that change over time Not started money
Opened 2026-11-07 · reviewed 2026-11-11 · docs/challenges/0007-rules-that-change-over-time.md
Watches 2 files
  • app/models/community.rb
  • app/models/meal_resident.rb

The challenge

When the community changes a pricing rule, each dinner keeps the rule that was in force on its own date.

The case that breaks it

  1. The community raises the age for full price from 12 to 13, starting March 1.

  2. An admin changes the setting on February 20.

  3. On February 21, a parent signs up their 12-year-old for a February 25 dinner. The child is charged half price, by the new rule, though that dinner is before March 1.

Where we stand

  • The price ages are two community settings, free_below_age and full_price_age, with no date (Community#multiplier_for_age in app/models/community.rb).

  • A sign-up copies its price into meal_residents.multiplier when it is made (MealResident#set_multiplier in app/models/meal_resident.rb). So a change never reaches a sign-up already made, and settled dinners cannot change.

  • The cost cap is copied to each meal when the meal is created (Meal#set_cap), so the same holds for the cap.

  • The gap: a sign-up made after a change, for a dinner dated before the change, uses the new rule.

Options

  1. Rules with a start date. A table of price rules, each with the date it starts. A sign-up uses the rule in force on the dinner’s date. Changing a rule means adding a row, never editing one.

  2. Refuse the change while unsettled dinners are dated after it would apply. Simpler, but it blocks the admin.

  3. Leave it, and tell admins to change a rule only on the day it starts.

9 Inflation and the limit on one bill Not started money
Opened 2026-11-07 · reviewed 2026-11-07 · docs/challenges/0009-inflation-and-the-bill-limit.md
Watches 1 file
  • app/models/bill.rb

The challenge

The app keeps working when prices rise for decades.

The case that breaks it

At 3% inflation a year, prices are about 10 times higher after 80 years. A dinner for 40 people that costs $300 today would cost about $3,000 then, and a big holiday dinner could pass $9,999.99. The cook cannot enter the cost, and the dinner cannot be settled as it happened.

Where we stand

  • One bill is capped at $9,999.99 by the model (app/models/bill.rb) and by its DECIMAL(12,8) column, which holds 4 digits before the point.

  • Sums (charges, balances) are DECIMAL(16,8), so they hold up to about $99,999,999.

  • The community cost cap has the same $9,999.99 limit (app/models/community.rb).

Options

  1. Widen the input columns when needed. A migration from DECIMAL(12,8) to DECIMAL(16,8) is cheap, and the code has one constant to change.

  2. Store money as whole units of 10^-8 dollars in bigint columns (also wanted by challenge 3). That holds about $92 billion, enough for any dinner for a very long time.

  3. Make the limit a community setting, so an admin can raise it without a deploy.

The challenge

The app works for a community that pays in another currency, or after the dollar itself changes (a new unit, or a smallest coin other than one cent).

The case that breaks it

A community in Japan uses the app. The yen has no cents, so “round to cents at settlement” rounds to a unit that does not exist, every screen shows “$”, and the cost input refuses “1500” without cents or reads it wrong.

Where we stand

  • The app serves one community forever (AGENTS.md), so this means changing that community’s currency, not running two at once.

Options

  1. A currency column on the community (ISO 4217 code), the number of minor-unit digits read from it, and every display and input going through it.

  2. Keep dollars, and write down that the app is for US communities.

11 The same answer after every deploy Not started money
Opened 2026-11-07 · reviewed 2026-11-07 · docs/challenges/0011-same-answer-after-every-deploy.md

The challenge

A deploy never changes what any dinner costs, unless the deploy is meant to.

The case that breaks it

  1. A deploy changes a sort, a rounding call, or how a guest is counted.

  2. Every unsettled dinner now computes a slightly different charge.

  3. Nothing fails: the specs build their own data, and the new numbers still add up to zero. The community is charged differently from what the screens showed the day before.

Where we stand

  • Settled dinners keep their stored lines, and triggers refuse changes to them, so a deploy cannot change them.

  • spec/support/oracle/plain_ledger.rb is a second ledger written only from the docs, and specs compare the real ledger with it on random dinners (spec/services/meal_ledger_against_plain_ledger_spec.rb, spec/tasks/stored_ledger_against_plain_ledger_spec.rb).

  • A replay of a production backup through the old and new code was done by hand in September 2026, and the tables were identical. It is not part of every deploy.

  • The daily ledger check compares settled balances with their source data, not one release’s numbers with another’s.

The challenge

Prove, not just test, that the money rules hold for every possible input: the lines of a dinner sum to exactly zero, each share is less than one unit from its exact value, and the cent rounding at settlement sums to zero.

The case that breaks it

A dinner with an input no test or random seed has tried (an odd mix of multipliers, a cap, a cook who spent nothing) makes the split leave one unit over. The property specs ran 10,000 seeds each on 2026-10-27 and found nothing, but 10,000 seeds is not every input.

Where we stand

  • Dafny proofs in proofs/ cover all three rules for every input (docs/proofs.md, issue #269):

  • the split: the shares sum to the total, each is less than one unit from its exact share, and the leftover units go to the shares that dropped the most, ties to the earlier position (proofs/LargestRemainderSplit.dfy);

  • the cent rounding: the rounded balances sum to exactly zero, each is less than one cent from its exact amount, and the cents go by the rule, ties to the lowest id; there are always enough balances to take the leftover cents, so Settlement.assert_candidates_cover_pennies! cannot fire on balances that sum to zero (proofs/CentRounding.dfy);

  • the lines of a dinner: the credits and the debits sum to the same amount on every branch (cancelled, nobody to charge, capped, subsidized, plain), and no cook is credited more than they spent (proofs/MealLines.dfy);

  • the sort into the tie-break order (proofs/TieOrder.dfy).

  • The Ruby is not proven.   • Not proven: what reads the rows into the ledger (bills, attendance, guests and the cap from the database), the conversion between dollars and units, and the order between two guests of one host, which no stored amount depends on.

  1. Dafny proofs of the split and the cent rounding, with the proven functions compiled or checked against the Ruby code by a spec that runs both on the same inputs.

  2. Prove in Dafny, test in Ruby: keep the Ruby code, and add a spec that compares it with the Dafny-compiled version on every seed.

Decision

The challenge

The money rules hold when parts of the system fail in the middle of a write: a dropped connection, a restarted database, a clock that jumps.

The case that breaks it

The browser sends a sign-up. The server commits it, but the network drops before the answer arrives. The browser tries again, and the person is signed up twice, or sees an error for a sign-up that worked.

Where we stand

  • bin/faults runs the real-server storm on a PostgreSQL of its own, through a proxy, while connections are cut, the database cannot be reached for a moment, PostgreSQL restarts and the server’s clock jumps. It loses some answers to writes, and the phone sends them again. Afterwards it checks the books, that no write was saved twice, and that no saved write was answered with an error when sent again (docs/fault-testing.md). A 12-second run is in bin/check and CI (spec/bin/faults_spec.rb).

  • A request that loses its database connection is answered 503 with a Retry-After, not 500 (lib/database_unreachable.rb).

  • Every write the browser sends again is safe to send twice. A bills save and a guest add need an Idempotency-Key (ADR 0009). The calendar writes, a guest remove and a settle take one (ADR 0015, spec/requests/api/v1/request_keys_spec.rb). Attendance writes carry a version, and a second send is answered 409 “stale” (ADR 0012). On a settled meal, a close, a cancel, a description or a cap that sends the value the meal already has is answered as saved (#280, app/controllers/concerns/settled_same_value.rb).

  • Not checked: a fault in Pusher or the mail server, a full disk, and a clock that moves on the database server itself (the app never reads it, spec/db/app_clock_spec.rb). No settle succeeded in the one-minute runs of 2026-11-12, so a settle sent again is checked by request specs only.

Options

  1. A fault-injection suite in the style of Jepsen: run bin/storm, and while it runs, drop connections (with a proxy such as toxiproxy), restart PostgreSQL, and move the clock. Afterwards, check every money rule and that every write that got a success answer is in the database once.

  2. Idempotency keys on every write (also in challenges 2 and 3), so a retry is always safe.

Decision

Both options, faults first (David, 2026-11-12). The fault suite is bin/faults, with its own PostgreSQL and a proxy written in Ruby instead of toxiproxy, so it never restarts the PostgreSQL the worktrees share. Its findings were fixed by DatabaseUnreachable, ADR 0015 and #280.

31 Replay any failure exactly Done proof

The challenge

Any failure a test finds can be run again, step for step, as often as needed.

The case that breaks it

A storm test fails once in 200 runs. The run used real threads, the real clock and real randomness, so it cannot be repeated. The failure is closed as “flaky”, and the real race is still there.

Where we stand

  • The money property specs use a seed, and a failure prints the command that runs that seed alone (spec/support/property_seeds.rb).

  • The request storm also runs under a seeded scheduler: one SQL statement runs at a time, and the seed picks whose (spec/support/simulation/scheduler.rb). The clock, sleep, rand and SecureRandom come from the seed while it runs (spec/support/simulation/determinism.rb), and every run starts from empty tables with ids from 1 (spec/support/simulation/world.rb). Two runs of one seed give the same statements in the same order and the same answers (spec/simulation/storm_spec.rb).

  • bin/check runs two seeds. SIM_SEEDS=<n> runs many, SIM_SEED=<n> replays one, and SIM_CLIENTS / SIM_SECONDS set the storm’s size (spec/support/simulation_seeds.rb). A failed seed prints the command that reruns it and writes every statement of the run to tmp/simulation/ (spec/simulation_seeds_spec.rb). A seed that passes drops its trace, so a search of thousands of seeds does not keep them all in memory. SIM_FIRST_SEED moves the first seed, and the Seed search workflow (.github/workflows/seed-search.yml) uses it to run a thousand new seeds every Sunday.

  • A race planted on purpose in the meal cap is found by some seed and found again by the same seed every time (spec/simulation/scheduler_planted_race_spec.rb).

  • The real-thread storms (spec/concurrency/request_storm_spec.rb, bin/storm) still use real time; a failure there still cannot be replayed. What the seed does not control yet is listed in #270.

Options

  1. Deterministic simulation (how FoundationDB is tested): run the app’s write paths in one thread, with a fake clock and a scheduler that picks which step runs next from a seed. Any failing seed replays exactly.

  2. Record the order of database statements in a storm run, so a failure can at least be read step by step.

Decision

Option 1, with the readable record of option 2: the seeded scheduler and its trace (docs/concurrency-testing.md, layer 5). Built on branch agent/replay-any-failure. What the seed does not control yet is #270.

  • 2026-11-12: David chose option 1 with a readable record: a scheduler that lets one SQL statement run at a time and uses a seed to pick whose turn it is, with a fake clock, plus a printout of the steps of a failed run. It is to drive the whole storm API (every action Storm::Client sends), and bin/check runs a few seeds; one setting runs many, another replays one. Work started on branch agent/replay-any-failure.

  • 2026-11-12: Built and closed. David chose to close the challenge once the work merges, and to list what the seed does not control in a new issue (#270) rather than keep this challenge open for it.

  • 2026-11-12: David approved a weekly workflow that runs new seeds (after an overnight search of 2700 seeds found no race).
